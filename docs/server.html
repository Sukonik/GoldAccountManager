Confirmation server

The one piece of server in a Tier 1 app. It confirms an email address once and signs a short statement that the user keeps in their packet.

First slice of Phase 1

Email links only. State is held in memory, so run one instance, and a restart forgets unfinished confirmations and app quotas. See known limits.

How a confirmation works

  1. Start. The app sends the address and the packet id. The server emails a link and returns a challenge id and a secret pickup value that only the caller has.
  2. Open the link. The user sees a page with a Confirm button. Opening the link changes nothing, because email scanners and link previews open every link in a message.
  3. Press Confirm. The server checks the token, applies the app's quota, and signs an attestation for that packet.
  4. Pick up. The app polls with the challenge id and pickup value and receives the attestation once. It goes into the packet, and no more email is needed.

Try it in two minutes

Needs Go 1.24 or newer. The demo uses throwaway keys and prints the email link instead of sending it.

go run ./cmd/goldd serve -dev
# in another terminal:
curl -s -X POST localhost:8080/v1/apps/demo-work/confirm/start \
  -H 'content-type: application/json' \
  -d '{"kind":"email","target":"sam@example.com","packetId":"pk_abcdefgh12345"}'
# open the link printed by the server (or GET /dev/inbox), press Confirm,
# then call .../confirm/pickup with the challengeId and pickup you got back.

What it is careful about

RiskWhat the server does
Mail scanners confirm for the userThe link only shows a button. A GET never confirms.
Someone else intercepts the resultThe attestation is released only to the caller holding the pickup secret, once. Wrong id, wrong secret, other app and expired all give the same 404.
Mail-bombing an address5 emails per address per hour and 20 per client per hour, per app.
Learning who is a memberThe reply to start looks the same for every address. The quota is applied only after the person proves control of the inbox.
Secrets leakingLinks and pickup values are stored hashed. Addresses, tokens and pickup values are never logged. The link page sends Referrer-Policy: no-referrer.
Header injection in emailAddresses with line breaks or extra recipients are refused before a connection opens. Subjects are encoded.
Plain-text mailSMTP needs STARTTLS unless the server is local, and a failed STARTTLS fails the send instead of downgrading.
Forged Host or X-Forwarded-ForLinks use the configured base address. The forwarded header is ignored unless trusted, and then only its last entry is used.
Moving an attestationThe signature covers the app id and packet id, so it fails on another packet or app.

These behaviours are tested, and each test was checked by deliberately breaking the code to confirm it fails. Several early tests passed for the wrong reason and were rewritten.

Free-tier limits per app

Each app has its own secret, so the same address in two apps gives two unrelated subjects. An app can cap how many different addresses it confirms (maxSubjects) and choose to block or waitlist new people after that. People already in a full app are always let back in.

Known limits

  • In-memory state. A restart forgets unfinished confirmations and app quotas and waitlists, so an app can exceed its cap after a restart. A durable store comes later.
  • Email only. Google sign-in, reply-email, Telegram, WhatsApp and SMS are planned, not built.
  • Single instance, and a per-process fixed-window rate limiter.
  • Build it with the newest Go patch release. A vulnerability scan finds dozens of standard-library issues in the server's code on older Go releases and none on the latest. The repository pins a patched toolchain, so go build fetches it.
  • Not externally reviewed.
